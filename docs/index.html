01 — Overview

What is RDK-B?

RDK-B sits between the hardware SoC/BSP layer and the operator's cloud management systems, providing pre-integrated components for Wi-Fi, routing, diagnostics, telemetry, device management, IoT, and application containerization.

Platform definition

RDKB components are open-sourced, vendor-independent, actively maintained, and each represented by one or more GitHub repositories. A HAL abstraction model means a single software stack can run on radically different SoC platforms — each component contains a logical grouping of related features, so a build only includes what a given device profile actually needs.

RDK-B component

A foundational, modular building block — open source, vendor independent, and actively maintained — represented by one or more GitHub repos. Components can be combined to create different software builds, and many are optional by design so a build only carries what its device profile needs.

Not an RDK-B component

Platform-specific Yocto manifests and meta-layers, board-specific build examples, vendor HAL implementations, and deprecated legacy code kept for history. These are integration artifacts, not reusable middleware.

02 — Architecture

The five-tier model

RDK-B's architecture reads like a cross-section: cloud-facing management at the top, silicon at the base, with the RDK-B middleware — the platform's largest tier — doing the work in between.

5

Cloud / ACS

Operator cloud: ACS, USP Controller, xConf, WebConfig, telemetry backends, crash collection, log aggregation.

4

Management Protocols

parodus / WebPA · usp-pa-vendor-rdk · tr069-protocol-agent · xconf-client · WebconfigFramework · T2 telemetry

3

RDK-B Middleware

OneWiFi, wan-manager, dhcp-manager, DSM, Dobby, BartonCore, and all 26 feature components. All communicate over RBUS.

2

HAL / BSP

rdkb-halif-* interface libraries and the vendor BSP — the boundary between RDK-B middleware and SoC firmware.

1

Hardware / SoC

Physical silicon: SoC CPU, Wi-Fi radio, modem chipset, Ethernet switch, Flash/RAM.

Tier 3 (RDK-B Middleware) is where nearly all feature development happens; Tiers 1–2 are vendor-owned and certified via RDK Ready.

03 — Standards

Architecture standards and governance

Every new or refactored component is held to the same rules for modularity, IPC, testing, and data modeling — so the platform stays consistent as more vendors and operators contribute to it.

Process & architecture governance
Modularity

Component scope

A component must implement one grouping of similar features only, so it can be added to a build solely when that feature set is needed.

IPC

RBUS is authoritative

All new contributions must use RBUS exclusively for inter-component IPC. Static analysis checks for regressions to sysevent, DMCLI, or CCSP.

Dependencies

Core vs. non-core

Non-core components must not depend on other non-core components — only on Core components, which are required across every device profile.

Testing

Unit tests & HAL suites

New components ship with isolated unit tests; HAL interfaces require an rdkb-halif-test-* suite before being declared stable.

Data model

Documentation is auto-verified

Supported data model elements are auto-discovered at runtime and diffed against submitted documentation before a contribution is accepted.

TR-181

Standard data models first

New data model names extend the TR-181 hierarchy where possible, using the X_RDK-<name> extension format otherwise.

Versioning

Semantic versioning, always

All components and HAL interfaces follow MAJOR.MINOR.PATCH; deprecated interfaces stay supported for at least two release cycles.

Build

Clean Yocto builds

No layer dependency cycles; recipes declare explicit LICENSE and SPDX identifiers; distro flags gate every profile-specific or optional feature.

Industry standards conformance

Where RDK-B functionality overlaps an established global standard, the implementation conforms to that standard's normative requirements rather than introducing a proprietary deviation.
